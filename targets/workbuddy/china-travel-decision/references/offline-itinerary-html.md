# 离线手机行程 HTML 交付规范

用户需要完整行程时，交付一份可保存到手机本地的旅行操作手册，而不只是把聊天摘要排版成网页。它要把已研究的信息组织成现场可查、可以采取下一步行动、遇到变化可以切换的内容。只使用当前环境实际具备的文件能力；没有文件输出能力时，给出完整源码和清楚的保存方式。

## 单文件和断网要求

- 交付单个 `.html` 文件。CSS、JavaScript、行程数据、图标和必要样式均内嵌在文件中。
- 不引用 CDN、远程脚本、远程样式表、网络字体、在线图片、地图瓦片或 API；不通过网络请求加载核心行程。
- 不要求本地服务器、安装、账号或服务工作线程。用户从手机本地文件打开后，主要内容和页面内交互仍应工作。
- 完整地址、入口/上下车位置、交通说明、预约入口名称、联系方式、核实日期和行动步骤直接写入页面。地图导航、购票、订位、电话等外部操作可做成链接，但逐项标明是否需要网络/移动信号；离线时仍能读取地址、候车/到达说明和当前状态。
- 不写入用户未提供的证件、付款或其他敏感信息。文件携带的行程信息应按用户可接受的隐私范围处理。

## 手机交互

使用适合手机竖屏的单列布局，中文清晰、对比足够、触控区域足够大。首先让用户一打开就找到“现在该做什么”，再按旅途任务展开细节。根据行程提供有实际用途的交互：
- 按日期/行程阶段切换，快速定位下一站、今天的交通和关键预约；
- 展开地点卡查看地址、入口、交通时间性质、步行/台阶、开放/预约、停留建议、休息条件、来源和备选；
- 选择主选/备选餐馆、活动或雨天/疲劳方案，并显示被选方案的地址和后续路线；
- 车票、住宿、活动、行李和出发前确认事项的状态/待办；允许用户在本机记下已订信息，但不预填虚假的预订成功状态；
- 预算区分已支付、已报价和估算；金额记录由用户填写时明确保存在本机的行为和清除方式；
- 快速复制/选取地址、拨号或地图/票务入口。复制、通话和外部服务是否能工作取决于设备与网络，提供可手动读取的文字后备。

核心内容不应依赖脚本才出现。页面交互失效时，行程仍须以可读文本完整显示。勾选状态可尝试保存在浏览器本地；由于本地文件在不同手机浏览器中的持久化行为可能不同，不能把本地保存作为查看行程的前提，并提供清空勾选状态的方式。

## 内容结构：按真实旅途任务组织

页面内容按用户的行程自然取舍，但完整出行通常覆盖以下模块：

1. **出发与抵达：** 往返站名、具体班次候选与查询时间、票种/购票状态、进站缓冲、抵达后的交通、上车/下车点、行李和酒店入住动作。
2. **住处比较：** 具名酒店、地址、确切日期与入住配置、已查总价/房态/取消条款，或未核实状态及准确的核价步骤；交通到车站和每日主要地点的时间性质；电梯、房型、早餐、寄存和老人实际需要的设施及证据。
3. **逐日现场路线：** 每段的时间顺序、明确起终点、推荐交通、门到门时间及来源/估算性质、步行距离或强度、上下车/入口位置、预约/票务、停留和休息安排。不要只写“打车前往”。
4. **景点与活动：** 具名地点或实际运营项目、适配理由、当日开放/场次、费用和预约状态、步行/台阶/接驳/厕所/座位等相关信息。未核实的行动便利性不能写成适合老人或无障碍。
5. **每餐怎么选：** 每个实际用餐片区列出主选和可接续的备选，含分店、完整地址、菜品、价位依据、营业/订位/排队核验状态、近期口碑要点和同伴适配情况。早餐也要有明确安排。
6. **变化时怎么办：** 对本次具体风险制作可执行分支，例如雨势达到什么程度时取消哪段、改去哪、如何到达、预约/费用怎么办；闭馆、售罄、延误、排队过长、同行者疲劳也按适用情况处理。替代方案必须能接回后续路线。
7. **现场支持与收尾：** 用户关心且与路线相关的厕所/休息点、药店/医疗服务等；返程前检查、最晚出发时间和未完成预订清单。涉及健康时只提供核实过的求助地点和联系方法。
8. **花费与证据：** 汇总适用的交通、住宿、活动、餐饮和市内交通预算，区分实际报价、参考价与估算；关键事实显示来源、核验时间和状态。

字段按用户需要与证据情况取舍，但不能把核心现场步骤删成一句建议。把待确认事项集中成“要做什么、何时做、从哪里确认、失败后怎么走”的任务卡；不能只堆“以现场为准”。用户到现场后不应为了找酒店地址、餐馆分店、预约条件或替代路线而回聊天重新搜索。

## 信息状态与在线边界

- 使用清楚一致的状态：已核实（带来源/时间）、已订/已购（仅在用户提供或实际确认后）、估算、推断、待确认。动态字段标明查询快照，不暗示仍然实时有效。
- 房态、票价、余票、天气、营业和场次无法实查时，保留可信的候选及其稳定信息，明确查询步骤、截止时点或影响，并提供可执行备选；绝不伪造当前可订或已预约。
- 说明离线页面可查阅已保存信息和使用页面内交互，但不能自动更新天气/客流/房态、加载在线地图、完成预订或保证电话接通。所有依赖网络/移动信号的动作均应醒目标注。
- 地图瓦片不离线打包。离线定位依靠文字地址、入口/上下车点、路段描述和用户已保存的导航信息；地图/导航外链作为在线辅助。

## 交付前现场任务走查

按本次旅客的约束，从 HTML 里模拟执行常见任务：

- 到出发站后，能否找到车次、站名、进站缓冲和抵达后的第一步？
- 抵达目的地后，能否找到酒店地址、上车/下车点、入住前后安排？
- 每天能否从当前地点看懂下一站怎么走、是否要预约、走路强度、在哪里休息或用餐？
- 餐馆关门/排长队、下雨、景点关闭、车次延误或同行人疲劳时，能否直接切到合适的方案并接回路线？
- 能否按页面办完离店、取行李、到车站和返程前检查？

若主要问题仍需回聊天或另行搜索才能采取行动，继续补充内容或明确真实限制。具备真实设备/浏览器时再做手机与断网交互检查；不具备时，只报告实际完成的静态/结构检查，不能声称现场可用已通过。

## 输出

1. 若有文件写入能力，将独立 HTML 保存为清晰文件名，例如 `行程离线版_YYYYMMDD.html`，并提供用户可打开的文件链接。
2. 若无法创建附件，输出完整、未截断的源码；告诉用户文件名和如何保存。根据已知手机系统给出简明步骤，设备未知时不要编造特定菜单路径。
3. 若有浏览器/文件预览能力，检查手机宽度下主要任务卡、地址和路线是否易找，切换日期/方案/待办是否可用；可行时断网检查核心内容和页面内交互。若无法真实断网或手机验证，清楚说明未验证。
4. 静态检查单文件没有必需外部资源或网络请求；可选外链注明联网要求。内容是否通过以现场任务走查为准，不能把“HTML可打开”当成旅行可用。
5. 行程复核后另存新版本并更新版本日期；不覆盖旧文件，除非用户明确要求。
